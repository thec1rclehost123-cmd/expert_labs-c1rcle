# 07. Partners, promoters and staff

Code: FE `components/partner-v3/partners/*`, `StudioPartnersClient`, `lib/api/{partner-data,partner-actions,staff-api}.ts`, `lib/partner/studio-partners-view-model.ts`; BE `routes/v2/partner/{partnerships,promoter-connections,discover,referral-links,event-catalog,organizations}.ts`, services under `packages/core/src/application/{partnerships,promoters,event-catalog,organizations}`.

## Partnerships (venue ↔ host) , Live
Aggregate: `id, hostOrganizationId, venueOrganizationId, venueId, initiatedBy host|venue, status, message, venueShareRate (int 0–50 | null), resolutionReason, resolvedAt, version`.
FSM: `pending → active | rejected | blocked | ended`; `active → ended | blocked`; rejected/blocked/ended terminal.
- Only the **counterparty** approves/rejects; either party may block; either may end (the counterparty cannot end a pending request); setting venue share is for parties of an **active** partnership only (no-op if unchanged).
- A venue-initiated request must come from the venue's owning org and name `hostOrganizationId`; host-initiated uses the actor's org. A live pair (pending/active) blocks a new request; a blocked pair returns 403. A partnership between two other orgs reads as 404.
- Routes: `GET /organizations/:org/partnerships` (names enriched, constant 3 batched lookups per page); `POST /partnerships` (`venue.manage`); `POST /partnerships/:id/{approve,reject}` (**`organization.read`**, so even `member` can answer); `{block,end,venue-share}` (`venue.manage`).
- Events: only `partnership.requested` is emitted (notification to the other party). Approve/reject/block/end emit nothing, so **requesters are not notified of answers**.
- Dashboard: Partners tab (venue/host segments `venues|hosts`, `promoters`, `staff`; sub-views `connected|discover|requests`); actions via `partner-actions.ts` (`POST /partnerships`, approve, reject). A venue-initiated request needs an existing venue (first venue used); host-initiated sends `venueId`. Keys per intent (`<studio>:<kind>:<id>:<action>`).

## Promoter connections (promoter ↔ host/venue) , Live
Aggregate: `id, promoterId, targetId (an organisation id for host and venue targets), targetType host|venue, initiatedBy promoter|target, status, message, resolutionReason, resolvedAt`.
FSM: `pending → active | rejected | blocked | revoked`; `active → revoked | blocked`; rest terminal. Recipient approves/rejects, either party blocks, **only the promoter revokes**. Counterparty must be an active org (404 otherwise); a live or blocked pair blocks a new request.
- Routes: `GET /organizations/:org/promoter-connections` (names); `POST /promoter-connections` (**`venue.manage`**, so a `member` cannot request); `POST /promoter-connections/:id/{approve,reject}` (`organization.read`); `{block,revoke}` (`venue.manage`). Emits `promoter_connection.requested`.
- Gotcha: the discovery DTO for a venue returns the **venue id** in `id`, but a connection request needs the **owning org id** (the dashboard sends `candidateOrganizationId`).
- Promoter studio tabs: `active | incoming | pending | declined | discover`; filter `all|venues|hosts`.

## Discovery
`GET /organizations/:org/discover-partners` (`type, q, cursor, limit ≤ 100`; the dashboard uses `limit=100`). Reads at most **200 active orgs and 200 active venues** (`BROWSE_CAP`), unordered, so partners beyond the first 200 are invisible. Live-pair counterparts are hidden; id-offset cursor; `verified` always false; `city` always null for orgs. Orgs with no `members` array are skipped; host/promoter kind derives from the union of member capabilities.

## Promoter assignments and referral links
- **Assignment** (`POST /events/:id/promoter-assignments`, `event.update`): `{promoterId, ratePercent?, flatPaise?, tierRates?}`; terms frozen `{version:1, ratePercent ?? 15, flatPaise ?? 0, tierRates?}`. Status `active | ended | suspended`; ended via `POST /promoter-assignments/:id/end` (idempotent; header validated but not enforced). Not checked: that the promoter org exists or has an active connection, duplicate active assignment for the same event/promoter, or that the event is still open. Writes a `promoter_assignment.created` notification directly to the promoter org.
- **Contract defect (verified):** `promoterAssignmentDtoSchema.status` is `z.enum(['active','ended'])` (`packages/contracts/src/contracts/event.ts:375`) but the model also has `suspended`; a suspended assignment would fail response validation (500) on `GET /events/:id/promoter-assignments`. `GET /promoters/:id/events` filters to active so it is safe.
- **Referral links** (`ReferralLinkService`): link id deterministic `pl-` + sha256(`promoterId:eventId`)[:32] (second create returns the existing link); promoter code stable per promoter globally (explicit different code → 400); vanity alias claimed per `prefix` (the promoter org slug) and unique; attribution signature = HMAC over the canonical snapshot keyed by `magicTicketSecret` (falls back to `'dev-secret'` if empty; production is meant to fail to boot without it); `clicks`/`conversions` do not bump `version`; deactivate is soft. `create` auto-creates a **0%** assignment `pa-<eventId>-<promoterId>` if none exists, bypassing the 15% default. Routes: `POST /promoter-assignments/:id/referral-links` (promoter org), `GET|POST /events/:id/referral-links`, `POST /referral-links/:id/deactivate`.

## Catalog items (tiers, promos, tables)
All via `EventCatalogService`; `assertEventOwned` gives 404 for foreign events.
- **TicketTier:** `name, description, entryType, currency (INR), priceInPaise, quantity, status active|paused|sold_out, salesStartAt, salesEndAt, maxPerOrder, accessType ENTRY|VIP|VVIP|TABLE|PACKAGE|RSVP, audienceType GENERAL|MALE|FEMALE|COUPLE|GROUP, guestCount, pricingPhases[], doorPriceInPaise, benefits[], minAge, maxAge, minPerOrder, maxPerUser, tableConfig{capacity, minimumSpendPaise, redeemableAmountPaise, tableCount}, commissionEligible, version`. Invariants: RSVP cannot carry price/phases/door price/commission; non-RSVP price > 0; quantity ≥ 0; `guestCount` ≥ 1; min ≤ max per order; sales start < end; phases positive-priced, non-overlapping; phase dates accept `DD-MM` (next occurrence in Asia/Kolkata, end exclusive, wraps year) or ISO; `TABLE` needs `tableConfig`; `commissionEligible` defaults to `price > 0`.
- **PromoCode:** `code (uppercased), name, type public|private|single_use|multi_use, discountType percent|fixed, discountValue, discountFundingOwner platform|venue|host|promoter|shared, tierIds[] (empty = all), maxRedemptions, maxPerUser, redemptionCount, startsAt, endsAt, isActive`; no per-org uniqueness check; usability enforced at checkout (`assertPromoUsable`). Note the guest UI cannot yet enter promo codes.
- **TablePackage:** `name, capacity>0, pricePaise≥0, minSpendPaise|null, isActive`; create/list only.

## Staff, invitations and credentials , Live
Routes (`organizations.ts`): `GET|POST /organizations/:id/members` (POST adds an existing user by id), `PATCH|DELETE …/members/:userId`, `GET|POST …/invitations`, `POST /invitations/:id/revoke`, `POST /invitations/:id/accept`, `GET /auth/invitations/mine`. Members/invitations need `staff.manage` (owner/admin).
- Dashboard (Partners → staff): list members + invitations; invite via `PartnerStaffInviteDialog` (roles member/manager/admin; a "confirmed" checkbox); edit role; remove member; revoke invitation. Owners show a badge and cannot be removed (backend 422/400). `getStaffFromApi` handles partial failure.
- **Invitation lifecycle:** FSM `pending → accepted | revoked | expired`, all terminal; `expired` is computed on read (14-day TTL); owner cannot be invited; uniqueness per `(org, normalised email)` (`findPendingByEmail` uses a single filter plus code to avoid a missing composite index); accepting as an existing member closes the invitation and leaves the role unchanged.
- **Credential provisioning (`createInvitation`):** after saving the invitation, `credentialProvisioner.provisionLogin(email, displayName)` runs; a new account gets a 16-character temporary password (alphabet without look-alikes) and `rotationStore.setRequired(userId, true)`; an email with the accept URL (`${PARTNER_DASHBOARD_URL}/invitations/<id>/accept?email=…`) and **the temporary password in the body** is sent. Both steps are fail-open (never roll back the invitation); existing users are untouched; it fails fast if the email already belongs to a member.
- Accept path: email link → `/invitations/:id/accept` → sign in → forced password rotation → auto-accept → `setActiveOrg` + `resolveLandingPath`. See the missing email-match defect in `04-…`.
- Events emitted by organisation code: only `organization.created`, `organization.updated` (member and invitation changes emit nothing).
